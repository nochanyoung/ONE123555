## 1. 배경 및 문제 정의

### 1-1. 핵심 문제

청년은 **"이 매물이 괜찮은가"를 판단할 기준 자체가 없다.** 시세도, 등기부등본도, 정책 자격도, 계약 위험도 전부 따로 검색해서 스스로 짜맞춰야 하는데, 처음 계약하는 사람은 애초에 뭘 확인해야 하는지조차 모른다.

### 1-2. 근거 — 원광대 앞에서 실제로 일어난 일

| | |
|---|---|
| **시점** | 2019년 |
| **장소** | 익산시 신동 (원광대 앞 원룸 15곳) |
| **피해자** | 약 120명, 대부분 원광대 학생·취업준비생 |
| **피해액** | 약 60억원 (개인 최대 전세보증금 5,000만원) |
| **수법** | 중개인이 **"이 건물엔 전세 세입자가 없거나 1~2명뿐, 나머지는 다 월세"라고 속임.** 실제로는 전세 세입자가 다수 → 건물 경매 시 후순위 세입자는 한 푼도 못 받음 |
| **결말** | 범인 징역 13년 6개월 확정 (2022. 1. 상고 기각). KBS 추적60분 방영 |

출처: [전북일보](https://www.jjan.kr/article/20190407669861) · [나무위키](https://namu.wiki/w/%EC%9D%B5%EC%82%B0%20%EC%9B%90%EB%A3%B8%20%EC%A0%84%EC%84%B8%EA%B8%88%20%EC%82%AC%EA%B8%B0%EC%82%AC%EA%B1%B4) · [매일신문(추적60분)](https://www.imaeil.com/page/view/2019060722481563014)

> **피해자 120명이 속은 것은 딱 한 가지 — "이 건물엔 전세가 없다"는 말이었다.
> 확정일자 부여현황 한 장이면 확인되는 거짓말이었다.**

### 1-3. 지역 특수성 — '연세' 관행

익산 대학가는 **연세**(1년치 임대료 선납)가 기본 계약 형태다. 구축 원룸 연세 400만원대, 신축 500~700만원대, 보증금 20~50만원. 월세 매물이 거의 없다. ([전북도민일보](https://www.domin.co.kr/news/articleView.html?idxno=1454514&sc_section_code=S1N8))

**직방·다방 등 기존 부동산 앱은 '연세'라는 계약 유형 자체를 지원하지 않는다.** 학생은 자기가 낼 돈이 적정한지 비교할 방법이 없다.

## 2. 목표

### 2-1. 제품 목표

> **파편화된 주거 데이터(시세·계약위험·지원정책)를 매물 하나를 기준으로 한 화면에 모아주는 앱.**

### 2-2. 성공 지표

| 구분 | 지표 | 목표 |
|---|---|---|
| **발표** | 4개 화면 데모 무중단 완주 | 필수 |
| **발표** | 2019년 사건 → 체크리스트 기능으로 이어지는 서사 완결 | 필수 |
| **실사용** | 배포 URL에서 누구나 접근 가능 | 필수 |
| **실사용** | 체크리스트 완료 건수 | 발표 후 2주 내 30건 |
| **데이터** | 화면에 표시되는 시세·정책이 실제 공공데이터 기반 | 필수 |

### 2-3. 비목표 (이번에 하지 않는 것)

- 매물 중개·계약 체결
- 회원가입·로그인
- 임대인 대상 기능
- 법률 자문 제공 (조언은 "확인할 것" 안내 수준으로 한정)

## 4. 범위

### 4-1. 포함 (MVP)

| # | 기능 | 화면 |
|---|---|---|
| F1 | 연세 포함 시세 목록 | 홈 |
| F2 | 매물 상세 정보 + 시세 적정성 | 상세 |
| F3 | 계약 전 필수 체크리스트 + 진단 결과 | 상세 → 체크리스트 |
| F4 | 청년 주거정책 조건 매칭 | 상세 → 정책 |

### 4-2. 제외 (근거와 함께)

| 제외 항목 | 이유 |
|---|---|
| 등기부등본 자동 연동 | **공개 API가 존재하지 않음.** 기관 계약 + 건당 유료. → 사용자가 직접 열람해 체크리스트에 입력하는 방식으로 대체 |
| 안전 매물 인증 배지 | 붙일 매물 DB가 없음 + **"안전 인증"의 법적 책임**을 학생 프로젝트가 감당 불가. → 진단 등급 표시로 대체 |
| 허위매물 필터링 | 매물 DB가 없으면 거를 대상이 없음. → 체크리스트 문항으로 대체 |
| 하자 신고·중재 플랫폼 | 임대인이 앱에 가입해야 성립하는 양면 시장. 3주 불가 |
| 사진 업로드 자동 하자 점검 | 곰팡이·누수 판별 모델이 없음 |
| 커뮤니티 사기 신고 게시판 | 실명 건물·중개사 대상 부정 게시물의 **명예훼손 리스크** |
| 회원가입·로그인 | 체크리스트 결과는 localStorage로 충분. DB·인증 불필요 |

## 5. 핵심 컨셉 — 문진표 → AI 진단서

병원에서 증상을 하나하나 설명하지 않아도 문진표만 체크하면 의사가 종합 진단을 내려주듯, 사용자가 매물 정보와 서류 확인 결과를 체크리스트로 입력하면 **하나의 진단서**가 나온다.

```
홈 (시세 목록)
  └─ 매물 상세
       ├─ [이 매물 체크하기] → 문진표 3단계 → 진단서
       └─ [지원 정책 보기]   → 조건 매칭 결과 → 신청 링크
```

## 6. 기능 요구사항

### F1. 홈 — 연세 포함 시세 목록

| ID | 요구사항 | 우선순위 |
|---|---|---|
| F1-1 | 익산시 신동 일대 임대 사례를 카드 목록으로 표시한다 | 필수 |
| F1-2 | 각 카드에 계약형태(연세/전세/월세/반전세) 배지를 표시한다 | 필수 |
| F1-3 | 모든 계약형태를 **월 환산가**로 함께 표시해 비교 가능하게 한다 | 필수 |
| F1-4 | 실거래 기반 항목은 "실거래 사례", 팀 확인 매물은 "매물"로 라벨을 구분한다 | 필수 |
| F1-5 | 연세 추정치에는 "추정" 배지와 "정확한 조건은 중개사무소 문의" 문구를 표시한다 | 필수 |
| F1-6 | 계약형태·가격대로 필터링할 수 있다 | 권장 |
| F1-7 | 상단에 서비스 한 줄 소개와 2019년 사건 배너를 표시한다 | 권장 |

**월 환산 공식** (전환율은 설정값으로 분리)

| 계약형태 | 월 환산가 |
|---|---|
| 연세 | `연세액 ÷ 12` |
| 월세 | `월세액` |
| 반전세 | `월세액 + (보증금 × 전환율 ÷ 12)` |
| 전세 | `보증금 × 전환율 ÷ 12` |

### F2. 매물 상세

| ID | 요구사항 | 우선순위 |
|---|---|---|
| F2-1 | 계약형태·보증금·연세/월세·관리비·면적·층·건축연도를 표시한다 | 필수 |
| F2-2 | 월 환산가와 **동네 평균 대비 비율**을 표시한다 (예: "평균보다 6% 저렴") | 필수 |
| F2-3 | 비교 표본이 5건 미만이면 비교를 표시하지 않고 "표본 부족" 안내를 낸다 | 필수 |
| F2-4 | `[이 매물 체크하기]` 버튼으로 F3으로 이동한다 | 필수 |
| F2-5 | `[지원 정책 보기]` 버튼으로 F4로 이동한다 | 필수 |
| F2-6 | 원광대까지 거리를 표시한다 | 권장 |

> **F2-3은 타협 불가.** 표본이 없는데 "평균 대비 15% 비쌈"이라고 표시하면 그것은 거짓말이다.

### F3. 계약 전 필수 체크리스트 → 진단서

#### 3단계 문진표

| 단계 | 파트 | 언제 쓰나 | 예시 문항 |
|---|---|---|---|
| 1 | **서류 확인** ⭐ | 계약 전, 서류 떼고 나서 | 근저당 설정액 / **선순위 세입자 보증금 합계** / 등기부 소유자와 임대인 일치 여부 / 대리인 계약 여부 / 무단 전대 여부 |
| 2 | **집 상태** | 집 보러 가서 | 곰팡이 / 누수 흔적 / 수압 / 방음 / 채광 / 창문·문 상태 |
| 3 | **내 조건** | 아무 때나 | 나이 / 연소득 / 재학·휴학 여부 |

| ID | 요구사항 | 우선순위 |
|---|---|---|
| F3-1 | 문항을 3단계로 나눠 표시하고 단계별로 진행률을 보여준다 | 필수 |
| F3-2 | **1단계에 "등기부등본·확정일자 부여현황 떼는 법"을 3줄 이내로 안내한다** | 필수 |
| F3-3 | 미응답 문항이 있으면 다음 단계로 넘어가지 못하게 한다 | 필수 |
| F3-4 | 응답은 localStorage에 저장해 새로고침해도 유지된다 | 권장 |
| F3-5 | 매물 없이도(직접 입력) 체크리스트를 시작할 수 있다 | 권장 |

> **F3-2가 이 제품의 핵심 가치다.** 2019년 피해자 120명이 하지 않은 것이 정확히 그것이다.

#### 진단서 — 5개 항목 + AI 소견

| ID | 항목 | 판정 방식 | 출력 |
|---|---|---|---|
| F3-6 | **시세 적정성** | `월환산가 ÷ 동네평균` | 저렴 / 적정 / 비쌈 |
| F3-7 | **계약 위험도** | `(선순위 보증금 + 근저당) ÷ 건물시세` + 치명 문항 | 안전 / 주의 / 위험 |
| F3-8 | **주거 품질** | 하자 항목 개수·가중치 | 양호 / 보통 / 미흡 |
| F3-9 | **비용 부담** | `(월환산가 + 관리비) ÷ (연소득÷12)` | 적정(≤20%) / 부담(~30%) / 과부담(>30%) |
| F3-10 | **받을 수 있는 정책** | 조건 매칭 (F4와 동일 엔진) | 목록 |
| F3-11 | **AI 종합 소견** | 위 5개 결과를 근거로 자연어 생성 | 요약 + 다음 행동 목록 |

**계약 위험도 판정 규칙**

```
부채비율 = (선순위 세입자 보증금 합계 + 근저당 설정액) ÷ 건물 시세
```

| 조건 | 등급 |
|---|---|
| 치명 문항 중 하나라도 위험 응답 | **위험** (부채비율 무관) |
| 부채비율 > 0.8 | **위험** |
| 부채비율 0.6 ~ 0.8 | **주의** |
| 그 외 | **안전** |

**치명 문항(is_critical)** — 2019년 사건 수법을 그대로 반영

- 확정일자 부여현황을 열람하지 않았다
- 중개인이 선순위 세입자 현황을 **구두로만** 설명했다
- 등기부상 소유자와 계약 상대방이 다른데 위임장을 확인하지 않았다
- 무단 전대(재임대) 여부를 확인하지 않았다

> **F3-12 (필수): 판정은 규칙이 하고, AI는 설명만 한다.**
> 이유 ① 시연 재현성 — 같은 입력에 항상 같은 결과가 나와야 한다.
> 이유 ② 책임 — "AI가 안전하다고 했는데 사고가 났다"를 만들지 않는다.

> **F3-13 (필수): 결과 화면 어디에도 "안전한 매물입니다"라고 쓰지 않는다.**
> 주어를 바꾼다 — **"입력하신 조건에서는 위험 신호가 발견되지 않았습니다."**

### F4. 청년 주거정책 매칭

| ID | 요구사항 | 우선순위 |
|---|---|---|
| F4-1 | 나이·소득·재학여부·계약형태·보증금 조건으로 신청 가능한 정책을 필터링한다 | 필수 |
| F4-2 | 정책별로 주관기관·지원내용·신청기간·신청 링크를 표시한다 | 필수 |
| F4-3 | 조건에 걸린 정책과 안 걸린 정책을 구분해 보여주고, 안 걸린 이유를 표시한다 | 권장 |
| F4-4 | 신청 링크는 새 탭으로 연다 | 필수 |
| F4-5 | 익산·전북 지역 정책을 우선 노출한다 | 권장 |

**정책 데이터**: 익산·전북·전국 청년 주거정책 **10~15건 수동 큐레이션**. (온통청년 API는 신청조건이 자연어라 자동 매칭이 불가능하므로 MVP에서는 수동 큐레이션으로 고정한다.)

## 7. 사용자 흐름

```
[홈] 신동 원룸 시세를 훑어본다
  │  "연세 400만원 = 월 33만원이구나"
  ▼
[상세] 관심 조건을 자세히 본다
  │  "동네 평균보다 6% 저렴하네"
  ▼
[체크리스트] 부동산 가기 전에 뭘 확인해야 하는지 배운다
  │  1단계: "확정일자 부여현황? 그런 게 있었어?"
  │  → 안내 보고 직접 열람 → 선순위 보증금 3,000만원 입력
  │  2단계: 집 보러 가서 하자 체크
  │  3단계: 내 나이·소득 입력
  ▼
[진단서] 종합 결과를 받는다
  │  시세 적정 / 계약 위험도 주의 / 주거 품질 양호 / 비용 부담 적정
  │  AI 소견: "이 건물엔 선순위 3,000만원이 있습니다. 계약 전에…"
  ▼
[정책] 받을 수 있는 지원을 확인하고 신청한다
```

## 9. AI 연동 사양

### 9-1. 사용 범위

**AI는 진단서 항목 ⑥ "종합 소견" 생성에만 사용한다.** 판정 5개(F3-6~F3-10)는 전부 규칙 기반이며 AI를 거치지 않는다.

### 9-2. 공급자 선택 — OpenAI

**팀 결정 (2026-08-10): OpenAI API 사용.**

비용 검토 결과, 이 프로젝트 전체 예상 사용량은 **약 46만 토큰**(진단서 230건 × 약 2,000토큰)이며 공급자 간 총비용 차이는 **최대 $5 미만**이다. 따라서 비용은 결정 요인이 아니며, 실제 기준은 ① 프로그램에서 제공하는 크레딧 유무 ② 팀이 이미 보유한 키다.

**공급자를 바꿔도 아키텍처는 동일하다.** 변경 대상은 SDK 패키지, 환경변수 이름, 모델 ID 세 가지뿐이며, 아래 9-3~9-6의 규칙은 공급자와 무관하게 그대로 적용된다.

| 항목 | 값 |
|---|---|
| SDK | `openai` (npm) |
| 모델 | **S3 착수 시 공식 문서에서 최신 저비용 모델 확인 후 확정.** 요약 생성 작업이므로 최상위 모델은 불필요 |
| 호출 위치 | Next.js Route Handler (`app/api/assessment/summary/route.ts`) — 서버 전용 |
| 출력 강제 | JSON Schema 기반 구조화 출력 (`strict` 모드) |

> **모델 ID를 지금 확정하지 않는 이유:** 모델 라인업과 가격이 자주 바뀌므로, 착수 시점에 공식 가격 페이지에서 직접 확인한다. 이 문서에 적힌 추정치를 그대로 믿고 코딩하지 말 것.

### 9-3. API 키 취급 — 필수 규칙 (공급자 무관)

| # | 규칙 |
|---|---|
| K1 | 키는 **환경변수 `OPENAI_API_KEY`** 로만 읽는다. 코드에 하드코딩 금지 |
| K2 | **`NEXT_PUBLIC_` 접두사를 절대 붙이지 않는다.** 붙이면 브라우저 번들에 그대로 노출된다 |
| K3 | `.env.local`은 `.gitignore`에 포함되어 있어야 한다. **커밋 전 반드시 확인** |
| K4 | 클라이언트 컴포넌트에서 AI SDK를 import하지 않는다 |
| K5 | 배포 시 Vercel 프로젝트 환경변수에 등록한다 |
| K6 | 키가 유출되면 즉시 콘솔에서 폐기하고 재발급한다 |
| K7 | 사용량 한도(spending limit)를 콘솔에서 설정해둔다 — 무한 루프 버그로 인한 과금 사고 방지 |

> **K2 위반은 이 프로젝트에서 가장 흔하고 가장 비싼 실수다.** `NEXT_PUBLIC_OPENAI_API_KEY`라고 쓰는 순간 배포된 웹페이지 소스에서 누구나 키를 읽을 수 있고, 그 키로 청구되는 요금은 팀이 부담한다.

### 9-4. 요청 사양

**입력**: 규칙 판정 결과 5개 + 매물 요약 (원시 응답 전체가 아니라 **판정 결과만** 보낸다)

**출력 형식**: 구조화 출력(`output_config.format`)으로 아래 스키마를 강제한다.

```
{
  summary:  string     — 2~3문장 종합 소견
  actions:  string[]   — 계약 전 해야 할 일 (3~5개)
  cautions: string[]   — 주의할 점 (0~3개)
}
```

### 9-5. 프롬프트 원칙

| # | 원칙 |
|---|---|
| P1 | 시스템 프롬프트에 **"법률 자문이 아니며, 확인해야 할 사항을 안내하는 역할"** 임을 명시한다 |
| P2 | 조언은 **"~하세요"(행동 안내)** 형태로 쓰고, **"안전합니다"(단정)** 형태를 금지한다 |
| P3 | 규칙 판정 결과를 **뒤집지 않는다.** 규칙이 '위험'이면 소견도 위험을 전제로 쓴다 |
| P4 | 익산·연세 맥락을 시스템 프롬프트에 포함한다 |

### 9-6. 오류 처리

| 상황 | 처리 |
|---|---|
| API 호출 실패 (네트워크·5xx·인증) | 진단서의 규칙 판정 5개는 **그대로 표시**하고, 소견 영역만 "소견을 불러오지 못했습니다 · 다시 시도" 표시 |
| 요청 한도 초과 (429) | 위와 동일. 재시도 버튼 제공 |
| 모델이 응답을 거부하거나 빈 응답 | 텍스트를 읽기 **전에** 응답 유효성을 확인. 무효 시 위와 동일 처리 |
| 스키마 검증 실패 | 파싱 결과를 그대로 렌더링하지 않고 실패 처리 — 깨진 JSON이 화면에 노출되지 않게 한다 |
| 응답 지연 | 소견 영역에 로딩 표시. 나머지 진단서는 즉시 렌더링 |

> **AI가 죽어도 앱은 살아 있어야 한다.** 진단서의 핵심 가치는 규칙 판정이고, AI 소견은 그 위에 얹는 층이다.

## 12. 팀 구성 및 일정

### 12-1. 팀 구성

| 역할 | 담당 | 이 프로젝트에서의 산출물 |
|---|---|---|
| 기획 및 리서치 | **노찬영** | 체크리스트 문항 설계, 정책 큐레이션 10~15건, 2019년 사건 자료 정리 |
| 마케팅 (어필 포인트) | **박재희, 박민준** | 발표 서사 구성, 문제 정의 근거 자료, 사용자 확보 방안 |

> ### ⚠️ 가용 시간은 16일이 아니라 **20시간**이다
>
> 작업 세션 5회 × 4시간 = **20시간**. 이 안에서 회의도 하므로 순수 제작 시간은 더 짧다.
> 이 숫자가 이 프로젝트의 모든 범위 판단의 기준이다.

| # | 이에 따른 운영 규칙 |
|---|---|
| C1 | **세션 시간은 "만드는 시간"이다.** 무엇을 만들지 정하는 논의는 세션 밖에서 끝내둔다 |
| C2 | 각 세션은 **다음 세션까지 각자 무엇을 완료할지** 정하고 종료한다 |
| C3 | **코드가 아닌 산출물은 세션 사이에 완성한다** — 체크리스트 문항(기획), 정책 목록(기획), 발표 서사(마케팅), 화면 시안(디자인). 세션에서 처음 논의하면 4시간이 통째로 사라진다 |
| C4 | **세션 5(8/24)는 리허설과 마감이다.** 그날 새 기능을 시작하지 않는다 |
| C5 | 세션 시작 시 **10분 안에 그날 목표 1개를 확정**하고 바로 작업에 들어간다 |

> **C3이 이 일정의 성패를 가른다.** 20시간 중 4시간을 "체크리스트에 뭘 넣을까" 논의로 쓰면 전체의 20%가 사라진다. 문항 설계는 기획 담당이 세션 밖에서 문서로 만들어 오고, 세션에서는 그것을 코드로 옮기기만 한다.

### 12-4. 밀렸을 때 잘라내는 순서

20시간은 4개 기능 + 배포 + 발표 준비에 빠듯하다. 밀릴 것을 전제로 **자르는 순서를 미리 정해둔다.** 세션 중에 "뭘 뺄까"를 논의하면 그 자체로 시간이 사라진다.

| 순서 | 자르는 것 | 대체 | 잃는 것 |
|---|---|---|---|
| 1 | 정책 매칭 엔진 (F4-1, F4-3) | 정책 정적 목록 + 신청 링크만 | 개인화. 서사는 유지됨 |
| 2 | AI 종합 소견 (F3-11) | 규칙 판정 5개만 표시 | "AI 활용" 어필. 제품은 그대로 성립 |
| 3 | 홈 필터 (F1-6), 거리 표시 (F2-6) | 없음 | 편의 기능 |
| 4 | Vercel 배포 | 로컬 시연 | 발표 후 실사용 |
| **없음** | **체크리스트 + 진단서 (F3)** | — | **이것을 자르면 프로젝트가 없다** |

> **F3는 어떤 상황에서도 자르지 않는다.** 2019년 사건 → 체크리스트로 이어지는 서사가 이 프로젝트의 전부이고, 나머지는 그 서사를 뒷받침하는 장치다.

### 12-5. 판단 기준

| # | 규칙 |
